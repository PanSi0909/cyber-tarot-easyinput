# 完成 12 步后，你应该学会什么

这 12 步不是要求你记住所有命令，也不是要求你完成一次课程后就能从零设计整台硬件。

它训练的是一套与 AI 合作开发硬件时可以反复使用的安全顺序：

> **先看清现状 → 说清目标和边界 → 小步实现 → 用证据验证 → 人工确认写入 → 观察真实结果。**

完成整套流程后，最重要的收获不是某一个 Host Action 功能，而是以后面对陌生工程时，知道应该按什么顺序开始。

## 四个阶段分别训练什么

| 阶段 | 表面上做了什么 | 真正训练的能力 |
|---|---|---|
| 01–03 · 读懂与基线 | 读工程、跑测试、建立协议纯逻辑 | 不急着改代码，先弄清现状、目标和不可触碰的边界 |
| 04–06 · 协议与实现 | 覆盖八键、接入事件和传输 | 把需求拆成配置、事件、协议和通道等可以分别验证的小层 |
| 07–09 · 通道与构建 | USB/BLE、能力声明、完整测试和构建 | 区分“代码逻辑正确”和“整个固件能够生成” |
| 10–12 · 写入与验证 | 差异审计、确认设备、烧录和 App 真机验证 | 区分“固件写入成功”和“真实功能成功”，并把危险操作交给人确认 |

这四个阶段依次回答四个问题：

1. 我面对的工程现状是真的吗？
2. 功能的边界和各层职责说清楚了吗？
3. 软件证据足够支持生成固件吗？
4. 正确设备上的真实现象符合预期吗？

## 应该带走的六种能力

### 1. 把模糊想法变成可观察结果

不要只说：

> 我想做一个 AI 按键。

应当说：

> 按下 KEY2 时打开指定应用一次；松开不重复；USB 和 BLE 双连接时不能双发。

AI 擅长完成边界明确的结果，但不能替使用者决定产品究竟应该解决什么问题。

### 2. 修改前先建立基线

开始开发前先回答：

- 当前工程能不能通过测试？
- 当前固件能不能构建？
- 当前板型、芯片和相关硬件资源是什么？
- 工作区原本有哪些修改？
- 哪些问题在本次修改前就已经存在？

这样出现失败时，才能判断是新改动造成的、原有代码造成的，还是环境没有正确激活。

### 3. 给 AI 划出不能越过的边界

本课程中反复保护了 GPIO、BOOT、GPIO8 共享电源、Flash 分区、USB/BLE 设备身份、HID 描述符、BLE GATT、冻结协议字段，以及 App 与固件各自负责的数据。

这些不是需要死记的通用答案，而是在训练一种习惯：

> **AI 可以负责阅读、实现和验证，但产品边界和危险操作必须由人确认。**

换到另一块开发板时，具体 GPIO 和 BOOT 规则会改变；“先查清并保护板级合同”的方法不会改变。

### 4. 把复杂功能分层验证

本次功能经过的主要链路是：

```text
配置
→ Keymap
→ 按键事件
→ 共享协议编码
→ USB/BLE 路由
→ App 接收
→ 操作系统执行真实应用动作
```

以后遇到故障，不要笼统地写成“硬件坏了”或“AI 没做好”，而要判断失败在哪一层：

- 配置是否被正确解析和保存？
- 按键是否产生了正确事件？
- 协议字段是否符合双方合同？
- USB 或 BLE 是否选择并发送了正确通道？
- App 是否建立并识别了本机映射？
- 操作系统是否真正执行了目标动作？

一次只定位一层，能够避免为了修复 App 问题而改 GPIO，也能避免为了掩盖固件双发而在 App 中增加去重。

### 5. 识别不同等级的证据

一次软硬件任务可能同时出现多种证据，它们不能互相代替：

1. **读源码**：只能证明静态代码看起来如此；
2. **宿主测试通过**：证明被测试的纯逻辑符合预期；
3. **固件构建通过**：证明源码和工具链能够生成固件；
4. **烧录成功**：证明固件已经写入目标设备；
5. **App 显示同步确认**：证明配置保存回执已经闭环；
6. **人工观察真实动作**：才证明最终功能在真实环境中可用。

因此，不能把“编译成功”写成“产品成功”，也不能把“AI 说已经完成”当成真机证据。

### 6. 为不可逆操作设置人工确认门

烧录、擦除、修改分区和设备身份都不应由 AI 自动决定。正确顺序是：

```text
只读检查
→ 确认目标设备
→ 展示写入范围
→ 人工输入唯一确认语
→ 执行写入
→ 恢复正常启动
→ 观察真机结果
```

这道确认门不是多余步骤，而是在保护开发板、已有固件和本机数据。

## 以后怎样复用这套方法

以后不必把所有任务机械地拆成 12 步。一个边界较小的功能，可以压缩成下面六步。

### 第一步：描述一个可观察结果

```text
我希望发生什么？
什么现象算成功？
什么绝对不能改变？
```

### 第二步：让 AI 先只读工程

```text
先读取工程结构、硬件合同和现有实现。
告诉我入口、链路、当前基线和风险，暂不修改。
```

### 第三步：验证修改前基线

```text
按工程约定运行现有测试和默认构建。
区分环境失败、测试失败、编译失败和链接失败。
```

### 第四步：进行最小修改

```text
先补能够证明缺口的失败测试，再做最小实现。
不要顺手重构，不要提前完成后续功能。
```

### 第五步：完成软件验收与差异审计

```text
运行全部测试和默认构建。
列出全部变化，确认硬件、身份、分区、协议和隐私边界没有被破坏。
```

### 第六步：最后才操作真机

```text
先只读确认目标设备，再由我明确授权烧录。
烧录成功后恢复正常启动，由我观察真实结果。
```

任务越危险、跨越的层越多，这六步就应该拆得越细；只改纯文字或纯逻辑时，可以相应缩短，但不能省略与风险直接相关的证据。

## 小白最容易产生的三个误解

### “我必须先学会全部代码才能开始”

不需要。第一步是学会定义结果、边界和验收证据。代码结构可以在具体任务中逐层理解。

### “AI 会帮我决定产品应该做什么”

AI 可以提供选项、分析取舍并完成实现，但“解决谁的什么问题”仍然需要使用者决定。

### “跑完流程就应该会设计整台硬件”

本课程首先训练工程协作、证据意识和风险控制。器件选型、原理图、PCB、电源完整性、结构设计和量产验证仍是后续独立知识。

## 不知道如何开始时的三句话

以后面对新功能或新工程，不知道第一条提示词该怎么写时，先填写：

```text
我想看到的真实结果是：________。
这次绝对不能改变的是：________。
能够证明成功的证据是：________。
```

然后再让 AI 只读工程、复述理解并报告基线。三句话没有写清楚以前，不急着要求 AI 改代码。

最后只需要记住：

> **先说结果，再读现状；先定边界，再做小步；先测软件，再写设备；最后由人观察。**
