# 第 3 课实践：把语音和旋钮接入网页流程

这一课解决的不是“加一个语音按钮”，而是让实体按键、语音转写、普通键盘和鼠标进入同一套可观察、可恢复的占卜流程。

## 课程目标

- S1 首次开始时播放一次启动提示；
- S2 进入四种牌阵选择；
- S3 把语音转写放入当前问题草稿；
- 用户能修改识别文字，确认后才写入会话；
- 麦克风不可用时仍能用普通文字继续；
- 旋钮完成选择和确认，尽量不中途拿起鼠标。

## 当时基线

早期版本已经有单轮抽卡、结果锁定和刷新恢复，但输入主要围绕普通网页操作。第 3 课从早期站点基线开始，把 S1–S3 和旋钮组织成第一条完整的 EasyInput 交互链路。

## 范围与禁止事项

本课只处理启动、牌阵、问题输入和抽牌体验。它明确不接入真实 AI、不实现历史统计、不修改固件、不操作 EasyInput App 中已经稳定的键位，也不发布未验收的正式版本。

## 实现思路

1. 用统一动作层接收鼠标、键盘和开发板输入，避免同一功能维护三套代码。
2. 把问题分成“识别草稿”和“已确认问题”；只有确认动作能改变牌局会话。
3. 在用户首次交互中播放启动提示，满足浏览器自动播放限制。
4. 用明确状态表示待机、输入中、等待确认、失败和完成。
5. 牌阵确认后才洗牌；揭牌后锁定结果，刷新只恢复而不重新随机。

## 关键转折与踩坑

- **固定文字不是可见表单**：最初把硬件指令显示成页面输入区，后来改成后台接收器，让用户只看到业务状态。
- **隐藏接收器仍需要焦点**：窗口切换后指令可能进入错误位置，因此补充窗口恢复、点击和粘贴后的焦点管理。
- **语音完成不等于问题确认**：识别结果必须允许检查和修改，旋钮短按只确认问题，不能同时抽牌。
- **本地文件不等于真实部署**：直接打开 `file://` 会带来模块和权限差异，最终统一使用本地 HTTP 验收。

## 人与 AI 如何分工

- 人决定哪些操作必须连续、哪些状态不能丢失，并完成真实开发板观察。
- AI 帮助拆分状态、统一输入入口、编写测试并定位焦点问题。
- 浏览器和真机负责提供证据；“代码看起来正确”不能替代实际操作。

## 验收证据

| 层级 | 本课证据 |
|---|---|
| 源码 | S1–S3、牌阵、问题草稿和统一动作入口进入 Git 历史 |
| 自动测试 | 当时分支回归通过；当前行为继续由 `main` 测试覆盖 |
| 浏览器 | 本地 HTTP 下走通启动、输入、抽牌、刷新恢复，无新增控制台错误 |
| 实体硬件 | S1、S2、S3、旋钮选择和短按完成真实流程 |

详细时间线见 [`QA.md`](../../QA.md)。

## 读者练习

1. 不用开发板，先用数字键和方向键完成“时间之流”。
2. 输入一段文字但不要确认，刷新后观察它与已确认问题的区别。
3. 拒绝麦克风权限，确认普通文字仍能完成流程。
4. 写下三类证据：自动测试证明什么、浏览器证明什么、真机证明什么。

## 当前版本中的变化

最终版本继续保留第 3 课的统一输入与问题确认原则，并把 S3 扩展到追问和学习笔记。牌面、学习模式、周期洞察和 S8 返回是后续课程加入的能力，不应倒推成第 3 课当时已经完成。
